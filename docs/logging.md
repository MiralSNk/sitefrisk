# Логирование и трассировка

Единая система наблюдаемости для четырёх сервисов на трёх языках.
Общая здесь **не библиотека, а контракт**: библиотеки между Go, Java,
Python и TypeScript не существует, поэтому согласован формат строки
и набор имён полей.

## Формат

JSON Lines: один объект на строку, без переносов внутри. Выбран не ради
моды: `grep` ищет подстроку, а `jq` фильтрует по полю. Когда один запрос
проходит через три сервиса, собрать его путь можно только фильтром по полю.

Побочная выгода: многострочное сообщение (например, предупреждение Spring
Security) остаётся **одной** записью — переводы строк экранируются. В
текстовом логе оно развалилось бы на пять нечитаемых строк.

## Обязательные поля

| Поле | Значение | Правило |
|------|----------|---------|
| `ts` | время | RFC3339 с миллисекундами, **UTC** |
| `level` | уровень | только `debug` / `info` / `warn` / `error` |
| `service` | имя сервиса | `scanner` / `auth` / `ml` / `web` |
| `msg` | сообщение | **константа**, см. ниже |
| `trace_id` | сквозной id запроса | 32 hex, см. «Трассировка» |
| `err` | текст ошибки | только при `warn` / `error` |

Доменные поля добавляются свободно: `scan_id`, `user_id`, `collector`,
`topic`, `partition`, `status`, `duration_ms`, `path`.

## `msg` — константа

    // нет
    log.Printf("scan %s failed: %v", scanID, err)

    // да
    logger.ErrorContext(ctx, "scan failed", "scan_id", scanID, "err", err)

С константным `msg` можно спросить «сколько сканов упало за час» одной
группировкой. С интерполяцией каждая строка уникальна, группировать нечего,
и логи снова читаются глазами. Плюс `scan_id` становится полем для фильтра,
а не куском текста внутри строки.

Язык `msg` — **английский**, во всех сервисах. Это ключ группировки, а не
текст для пользователя. Комментарии в коде при этом русские.

## Уровни

- `error` — сломалось то, что должно работать; нужна реакция человека
- `warn` — сработал запасной путь или внешняя система повела себя плохо,
  но мы продолжили
- `info` — факт жизненного цикла: сервис поднялся, скан начался/закончился
- `debug` — подробности для разбора, в проде выключены

Заблокированный SSRF-запрос — это `warn`: защита сработала как задумано.
«Не смог записать факты в базу» — `error`.

## Трассировка

Стандарт **W3C Trace Context**, заголовок `traceparent`:

    traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
                 ^^ ^- trace-id (32 hex) -^ ^- span-id (16) -^ ^^ флаги

Стандарт, а не свой `X-Trace-Id`, потому что его нативно читает
OpenTelemetry: переход на настоящий трейсинг не потребует переделки
проброса.

- `trace_id` проходит через все сервисы **неизменным**
- `span_id` каждый сервис генерирует **свой** — он идентифицирует хоп
- заголовок приходит извне, поэтому **валидируется**, а не принимается
  на веру: четыре части, длины 2/32/16/2, только `[0-9a-f]`, версия не
  `ff`, trace-id и parent-id не из одних нулей
- невалидный или отсутствующий заголовок → начинаем новую трассу
- `traceparent` возвращается в заголовке ответа, чтобы `web` мог показать
  код обращения пользователю

Путь трассы:

    браузер
      └─> web          нет traceparent -> сгенерировать (edge системы)
            ├─> auth    передать заголовок как есть
            └─> scanner передать заголовок как есть
                  └─> Kafka   traceparent в ЗАГОЛОВКИ СООБЩЕНИЯ
                        └─> ml  прочитать из заголовка, положить в контекст

Переход через Kafka — место, где трассу теряют: HTTP-заголовка там нет, но
у сообщения есть свои `Headers`.

### Чего у трассы нет

`trace_id` живёт **в рамках запроса**. Строки старта и остановки сервиса
его не имеют, и это правильно. Фоновые задачи (релей outbox, консьюмер
Kafka) работают не по запросу — там трассу надо начинать самим либо
восстанавливать из заголовка сообщения.

## Реализация по сервисам

| Сервис | Инструмент | Как доезжают контекстные поля |
|--------|-----------|-------------------------------|
| scanner | `log/slog` (stdlib) | свой `slog.Handler` читает атрибуты из `context.Context` |
| ml | `logging` + `contextvars` (stdlib) | `contextvars`, не `threading.local`: каждый запрос Starlette идёт в своей asyncio-задаче со своей копией контекста |
| auth | SLF4J/Logback + формат ECS | MDC; очистка в `finally` обязательна — MDC это ThreadLocal, а Tomcat переиспользует потоки |
| web | свой логгер на `console` | явно: `AsyncLocalStorage` недоступен в Edge-рантайме, где живёт middleware Next |

Ни один сервис не получил новой зависимости ради логов.

`LOG_LEVEL` и `LOG_FORMAT` читаются из окружения. У `auth` `LOG_LEVEL`
управляет **только** `com.sitefrisk`: `logging.level.root=debug` включил бы
DEBUG всего Spring и дал ~400 строк на один старт.

## Известные отклонения

- `auth` пишет в схеме **ECS**: `@timestamp` вместо `ts`, `log.level`
  вместо `level`, `message` вместо `msg`, `service.name` вместо `service`.
  `trace_id` и `span_id` из MDC попадают плоскими полями, то есть
  фильтрация по трассе работает. Приведение имён — долг, нужен свой
  `StructuredLogFormatter`.
- `auth` пишет время с наносекундами (9 знаков) вместо миллисекунд (3).
  На сортировку не влияет.
- Сообщения uvicorn (`"Started server process [7]"`) содержат
  интерполяцию — это код библиотеки, не наш.

## Что не логируется никогда

Логи кажутся безобидными: их грепают, вставляют в issue, шлют в чат,
отправляют в Loki с более широким доступом, чем у базы. Секреты утекают
через наблюдаемость.

- заголовки `Authorization`, `Cookie`, `Set-Cookie`
- JWT целиком (можно `jti` или первые 8 символов)
- refresh-токены, `token_hash`, `password_hash`
- строки подключения — там пароль внутри
- URL с userinfo (`https://admin:pass@host`) — отсюда `u.Redacted()`
- тела запросов на логине и регистрации

## Чтение логов

    make logs-json              # всё в едином виде
    make errors                 # только warn и error
    make trace T=<trace_id>     # весь путь одного запроса
    make find F=user_id V=u-42  # строки по значению поля
    make traces F=user_id V=u-42  # уникальные trace_id по полю
    make slow MS=500            # медленные запросы
    make top                    # сводка: строк и трасс на сообщение

`scripts/logs.jq` нормализует наш формат и ECS к одному виду, сохраняя
все остальные поля. Не-JSON строки отбрасывает.

Фильтры можно отлаживать на сохранённом файле, не трогая контейнеры:

    docker compose logs --no-log-prefix --since 1h > /tmp/saved.log
    make errors LOG_SOURCE="cat /tmp/saved.log"

### Как найти нужный trace_id

Его **не ищут** — его получают:

1. называет пользователь (мы показываем код обращения на экране ошибки);
2. он есть в строке с ошибкой — начинай с `make errors`;
3. ты знаешь бизнес-признак → `make traces F=<поле> V=<значение>`,
   потом `make trace` по найденному.

Третий путь работает только если поле попало в лог. Поэтому доменные
поля в контракте — не украшение, а мост от жалобы пользователя до строки.пше
